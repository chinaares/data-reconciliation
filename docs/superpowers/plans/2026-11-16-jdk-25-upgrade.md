## 1. 结论摘要

**有风险，但风险全部落在依赖版本上，与 JDK 25 本身无关。**

- 唯一的**硬阻塞**是 Lombok：1.18.34 在 JDK 25 上必然编译失败，必须升级。
- 另有 3 项非阻塞项（Netty 的 `sun.misc.Unsafe` 终态弃用警告、Hutool 的时区告警噪音、Surefire 无官方 JDK 25 支持），其中 Netty 那项是**面向未来 JDK 的前瞻性风险**，今天不影响功能。
- 项目自身 63 个 Java 源文件不含任何 `sun.misc` / `Unsafe` / 时区 / JDK 内部 API 用法，因此**不存在 JDK 25 移除类 API 造成业务代码编译或运行失败**的问题。
- 全部实测组合中，**最高可行配置 108/108 测试通过**。

| 风险 | 等级 | 是否阻塞 | 处置 |
|---|---|---|---|
| Lombok 1.18.34 不支持 JDK 25 | 高 | **是** | 必改 → 1.18.48 |
| Netty（经 Redisson）调用已弃用的 `sun.misc.Unsafe` | 中 | 否 | 建议 → Redisson 3.52.0 |

## 4. 风险清单

### 4.1 Lombok —— 唯一硬阻塞（必须改）

P1 完整失败链：

```
java.lang.ExceptionInInitializerError
  at lombok.javac.apt.LombokProcessor.placePostCompileAndDontMakeForceRoundDummiesHook(LombokProcessor.java:174)
  at lombok.core.AnnotationProcessor.init(AnnotationProcessor.java:213)
Caused by: java.lang.NoSuchFieldException: com.sun.tools.javac.code.TypeTag :: UNKNOWN
  at lombok.permit.Permit.getField(Permit.java:144)
  at lombok.javac.JavacTreeMaker$SchroedingerType.getFieldCached(JavacTreeMaker.java:171)
  at lombok.javac.Javac.<clinit>(Javac.java:186)
```

JDK 25 移除了 Lombok 依赖的 `com.sun.tools.javac.code.TypeTag.UNKNOWN` 字段。

**版本矩阵**（来源：Lombok 官方 changelog 与 JDK 兼容矩阵）：

| 目标 JDK | 最低 Lombok 版本 |
|---|---|
| JDK 25 | 1.18.40 |
| JDK 26 | 1.18.46 |
| JDK 27 | 1.18.48 |

**建议升到 1.18.48**（当前最新），理由：

- 1.18.40 起才有 JDK 25 支持；
- 1.18.44 修复了 JDK 25 上 `val` / `@ExtensionMethod` 可能触发**伪 javac 报错**（编译其实成功但报错，issue #3947）。本项目当前未使用 `val`，但升到 1.18.48 可一次性规避；
- 1.18.48 同时具备 JDK 26/27 的前置支持。

风险等级：**低**。Lombok 是纯注解处理器，P2–P6 在本项目 63 个源文件上零改动通过。

### 4.2 Netty 的 `sun.misc.Unsafe` 终态弃用（中等，前瞻性）

Redisson 3.27.2 → Netty 4.1.107，在 JDK 25 上产生：

```
WARNING: A terminally deprecated method in sun.misc.Unsafe has been called
WARNING: sun.misc.Unsafe::objectFieldOffset has been called by io.netty.util.internal.PlatformDependent0$4
WARNING: sun.misc.Unsafe::objectFieldOffset will be removed in a future release
```

- **今天不影响功能**：P2–P5 全部 108/108 通过；JDK 21 下无此告警（P6）。
- **风险在未来**：JDK 已把该方法标记为 *terminally deprecated*，JDK 一旦移除，Netty 的 `PlatformDependent0` 需要有 fallback。Netty 4.1.118+ 才有 JDK 24/25 相关适配。

**缓解**：Redisson 升到 3.52.0（3.x 最新稳定版）→ 传递依赖 Netty 4.1.127。升后告警项从 `objectFieldOffset` 变为 `allocateMemory`（P5），说明 Netty 仍在使用 Unsafe，但版本已进入有适配的分支。

> 若希望彻底消除该告警，需等 Netty 切换到非 Unsafe 的内存分配路径，或改用 Redisson 4.x（**大版本**，API 变更面大，本次不建议）。

### 4.3 Hutool 5.5.8 的时区告警噪音（低）

JDK 25 上每个测试 JVM 刷 56 行：

```
WARNING: Use of the three-letter time zone ID "ACT" is deprecated and it will be removed in a future release
```

**已定位到来源**：`cn.hutool.core.date.DateUtil`（Hutool 5.5.8，2021 年版本）。单独调用 `DateUtil.now()` 即可复现，单独调用 `StopWatch` 则无告警。Hutool 5.8.48 下告警归零（P4/P5）。

- 功能无害，但会淹没 CI 日志；且 Hutool 5.5.8 距今 4 年，本身也该升级。

### 4.4 Surefire 3.2.5 无官方 JDK 25 支持（低）

P2–P5 证明 3.2.5 在 JDK 25 上**能跑通**（108/108），但它是 2024-01 的版本，官方 JDK 25 支持自 **3.5.4** 起才加入。建议升到 3.5.4+（当前最新 3.6.1），避免 CI 上出现未覆盖的边界问题。

### 4.5 已确认**不存在**的风险

- 项目源码无 `sun.misc` / `Unsafe` / `TimeZone` / `ZoneId` 用法 → 不受 JDK 25 移除类 API 影响。
- `maven-compiler-plugin` 3.13.0 + `jdkToolchain` 25：正常。
- Maven 3.10.0 自身跑在 JDK 25 上：正常。
- Redisson + embedded-redis 1.4.3 在 JDK 25 上：正常（全部 Redis 相关测试通过）。
- JDK 25 未引入影响本项目 API 的行为变更。

## 5. 执行方案

### 5.1 最小风险路径：只挪 toolchain，字节码留在 21

**关键决策：`<main.java.version>` 保持 21，只把 `<jdkToolchain><version>` 改成 25。**

理由：

- 产物字节码仍是 Java 21，且用 `--release 21` 锁定 API 面 → **下游的运行时要求不变**（仍需 Java 21+），无需同步升级运行时；
- **但下游的依赖图变了**：本库以 compile scope 传递 Redisson 3.52.0 + Netty 4.1.127.Final，且公开 API 直接暴露 `org.redisson.api.RedissonClient` 类型。下游若自带 Redisson/Netty 版本管理（如 Spring Boot BOM），请确认解析出的版本不低于该值；
- 自己提前在 JDK 25 上跑编译与测试，提前暴露运行时问题；
- 若后续要用 Java 25 语言特性，再单独提一次变更。

P2/P4/P5 已验证该路径在 JDK 25 上 108/108 通过。

## 6. 踩坑记录

1. **`<vendor>` 必须与实际 JDK vendor 一致**，否则 Maven **静默回落到默认 JDK**（不报错，但实际用的不是 25）。本机 25 是 `Eclipse Adoptium` → `adoptium`。
2. **`source`/`target` 必须与 toolchain 匹配**。JDK 21 的 javac 配 `-source 25 -target 25` 直接失败：
   ```
   错误: 无效的源发行版：25      # error: invalid source release: 25
   ```
   → 若 toolchain 是 25，`main.java.version` 可以是 21 或 25；若 toolchain 是 21，`main.java.version` **必须** ≤ 21。
3. **增量编译会掩盖上述错误**。`mvn compile` 在类文件已是最新时不会重新编译，从而「成功」；必须 `mvn clean compile` 才能暴露不匹配。
4. **Maven 自身运行的 JDK 与 toolchain 无关**。`JAVA_HOME` 决定 Maven 进程用哪个 JDK，`<jdkToolchain>` 决定编译/测试 fork 用哪个 JDK。两者可以不同（例如 Maven 跑在 21、编译测试跑在 25）。
5. **`maven.compiler.source/target` 与 `main.java.version` 是两套属性**，compiler 插件实际用的是 `${main.java.version}`；改一处要确认另一处。

| 等级 | 问题 | 修复 |
|---|---|---|
| **Critical** | `.github/workflows/ci.yml` 仍装 JDK 21、写 `<version>21</version>` 的 toolchains.xml，而 pom 已请求 `{version=25}`。surefire 在 toolchain 不匹配时**硬失败**（`Requested toolchain specification did not match any configured toolchain: {version=25}`）→ 合并后 CI 必红；而 compiler 插件在同样情况下**静默回落**到运行 Maven 的 JDK，编译阶段不报错 | `ci.yml`：`java-version` → 25、toolchains.xml `<version>` → 25、`<vendor>` → adoptium、注释同步；新增「Verify the tests really ran on JDK 25」一步，断言 surefire fork 出的测试 JVM 版本 |
| **Important** | 只用 `-source 21 -target 21`，javac 仍链接运行中 JDK 25 的平台类，Java 22+ API 可以混进「声称是 Java 21」的产物。「下游不受影响」只是假设，未经构建保证 | 编译改用 `--release 21`（ct.sym 锁定 API 面，越界调用直接编译失败），并删除随之失效的 `maven.compiler.source/target` 死属性 |
| **Important** | CLAUDE.md 写「Maven aborts when it cannot find one」——只对了一半：surefire 硬失败，compiler 静默回落 | 改写为两句，分别说明两种失败模式，并强调 `mvn compile` 成功不代表用了 JDK 25 |
| **Important** | CLAUDE.md 要求 `<vendor>` 必须匹配实际 JDK——不成立：pom 只请求 `<version>`，vendor 不参与匹配，决定 JDK 的是 `<jdkHome>` | 改写为：`<version>` 必须是裸主版本 `25`（写 `25.0.4.1` 匹配不上）、`<vendor>` 只是描述性标签、`<jdkHome>` 才是决定项 |
| **Important** | 报告称下游「完全不受影响」过宽：本库以 compile scope 传递 Redisson 3.52.0 + Netty 4.1.127.Final，且公开 API 直接暴露 `RedissonClient` 类型 | §5.1 收窄为「运行时要求不变」，另起一句说明传递依赖变化；`CHANGELOG.md` 增补依赖升级条目 |
